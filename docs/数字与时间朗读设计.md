# 数字与时间朗读设计（NumberReaderZh）

CrewChief 不把"1分23秒4"当成一句话录下来，而是在运行时把数字拆成若干个音频文件夹依次播放。拆分规则由
`NumberReader` 的语言实现决定。英文实现 `NumberReaderEn` 需要 **1052 个** `numbers/` 文件夹，中文只需要
**138 个** —— 这份文档说明为什么，以及中文的拆分规则是什么。

相关文件：

| 文件 | 作用 |
|---|---|
| [`src/NumberReaderZh.cs`](../src/NumberReaderZh.cs) | C# 实现，需拷贝到 `CrewChiefV4/NumberReaderZh.cs` |
| [`patches/crewchief-zh-numberreader.diff`](../patches/crewchief-zh-numberreader.diff) | 对 CrewChief 的改动（工厂分支 + csproj + 单元测试） |
| [`translations/numbers_zh.csv`](../translations/numbers_zh.csv) | 138 个文件夹的语料 |
| [`scripts/make_numbers_inventory.py`](../scripts/make_numbers_inventory.py) | 生成语料 + Python 镜像验证 |

## 1. 为什么中文只要 138 个而不是 1052 个

英文的数字文件夹里有大量**预录合成音**，因为英文数字连读会变形，拼接听起来很假：

- `1_01`…`2_59`（118 个）—— "one oh one" 到 "two fifty nine"，圈速专用
- `0point1`…`59point9`（599 个）—— "twelve point three"
- `1point0seconds`…`9point9seconds`（90 个）—— 带 "seconds" 的版本
- `point0`…`point99`（100 个）—— 百分位

中文数字**每个字的读音固定不变**：二十三就是"二十"+"三"，一百一十五就是"一百"+"一十"+"五"，没有连读变形。
所以只要录 0–99 加上位值词，其余全部拼接合成。这也是为什么中文实现不需要葡萄牙语那样的阴阳性变体
（`duas`/`dois`）。

代价是拼接点变多，听感上会比整句录音略碎。缓解办法见 §5 的整段录音机制。

## 2. 整数读法

`GetIntegerSounds` 支持 -99999 到 99999，按 万 / 千 / 百 逐级拆分，每级不足下一级时补"零"。

| 输入 | 输出文件夹序列 | 读音 |
|---|---|---|
| `0` | `0` | 零 |
| `23` | `23` | 二十三 |
| `100` | `1` `hundred` | 一百 |
| `105` | `1` `hundred` `oh` `5` | 一百零五 |
| `110` | `1` `hundred` `1` `10` | 一百一十 |
| `115` | `1` `hundred` `1` `15` | 一百一十五 |
| `200` | `2` `hundred` | 二百 |
| `345` | `3` `hundred` `45` | 三百四十五 |
| `1005` | `1_thousand` `oh` `5` | 一千零五 |
| `1050` | `1_thousand` `oh` `50` | 一千零五十 |
| `1500` | `1_thousand` `5` `hundred` | 一千五百 |
| `2000` | `2_thousand` | 两千 |
| `10500` | `1_ten_thousand` `oh` `5` `hundred` | 一万零五百 |
| `-5` | `minus` `5` | 负五 |

两条容易踩的规则：

**十的读法。** `15` 单独读"十五"，但跟在更高位后面必须读"一十五"（一百一十五）。所以 10–19 在有高位时
前面补一个 `numbers/1`。

**二和两。** 百位用"二"（二百），千位和万位用"两"（两千、两万），跟量词时用"两"（两秒、两分钟）。
20–99 里的二照常（二十三）。这不是随意选的 —— "两百"和"二百"都通行，但"二千""二秒"在口语里很别扭。

`allowShortHundredsForThisNumber` 参数对中文无意义。英文用它决定 115 读 "one fifteen" 还是
"one hundred and fifteen"，中文只有一种读法，实现里忽略这个参数。

## 3. 时间读法

`ConvertTimeToSounds` 把时间拆成 时 / 分 / 秒 / 十分位 四段，分别调用四个方法后拼接。

| 场景 | 输入 | 读音 | 说明 |
|---|---|---|---|
| 圈速 | `1:23.4` TENTHS | 一分二十三秒四 | |
| 圈速 | `1:23.0` TENTHS | 一分二十三秒 | |
| 圈速 | `1:03.4` TENTHS | 一分零三秒四 | 个位秒必须读前导零 |
| 圈速 | `2:23.4` TENTHS | 两分二十三秒四 | |
| 差距 | `0.8` TENTHS | 零点八秒 | |
| 差距 | `12.3` TENTHS | 十二秒三 | |
| 差距 | `12.7` SECONDS | 十二秒 | 精度截断，小数位丢弃 |
| 差距 | `2.0` TENTHS | 两秒 | |
| 剩余时间 | `15:00` MINUTES | 十五分钟 | |
| 剩余时间 | `1:30:00` MINUTES | 一小时三十分钟 | |

### 与英文实现的三处关键差异

**中文总是把单位词读出来。** 英文的 `GetMinutesSounds` 在后面还有秒数时会省略 "minutes"
（"one twenty three point four"），中文不能省 —— "一二十三"根本无法解析。

**"分"和"分钟"是两个词。** 圈速说"一分二十三秒"，剩余时间说"还剩十五分钟"。实现复用了
`numbers/minute` 和 `numbers/minutes` 这两个已有文件夹来承载这两个词，不需要新增：

| 文件夹 | 中文 | 用在 |
|---|---|---|
| `minute` | 分 | 后面还要读秒时 |
| `minutes` | 分钟 | 单独报时长时 |

**"秒"跟在整数部分后面，小数位再接。** 英文把 "point 4" 作为一个整体接在后面，中文的赛车播报习惯是
"二十三秒四" —— 所以 `GetSecondsSounds` 读出"秒"，`GetTenthsSounds` 只补数字。只有在没有整数部分时
（纯小数差距）才读完整的"零点八秒"。

中文口语没有"十分之几秒"的说法，所以 `tenth` / `tenths` 两个文件夹实现里用不到，只作为兜底录成"秒"。

### 3.1 钟点是另一回事（`GetTimeOfDaySounds`）

上面整节讲的都是**时长**。「现在几点」是**钟点**，两者中文说法完全不同——
「八小时零五分」是时长，「上午八点零五分」才是钟点。

这不是 `NumberReader` 的抽象方法，基类只管时长。钟点原本由
[`CommonActions.reportCurrentTime()`](CrewChiefV4/Events/CommonActions.cs:814) 直接拼片段，
顺序是 `hour + oh + minute + am/pm`——**英文语序**。中文有两处不同：

1. 上午/下午在**最前面**，不在最后
2. 小时后面要跟**「点」**

所以加了 `NumberReaderZh.GetTimeOfDaySounds(hour, minute, folderAM, folderPM)`，
`CommonActions` 里只留一个 `as NumberReaderZh` 的分支去调它。

**放在 `NumberReaderZh` 而不是调用方，是为了共用 `countWithUnit` 的量词规则**——
2 点要读「两点」不是「二点」，和「两圈」「两秒」是同一条规则，不该在调用方再实现一遍。

**没有新增音频。**「点」复用 `numbers/point`：钟点的点和小数点的点是同一个字、同一段录音。
其余片段（`alarm_clock/am`=上午、`pm`=下午、0–59、`oh`=零、`liang`=两、`minute`=分）语音包里都已有。

| 时刻 | 读音 | 说明 |
|---|---|---|
| 08:05 | 上午八点零五分 | 分钟个位要读前导零 |
| 08:00 | 上午八点 | 整点不读「零分」 |
| 14:05 | 下午**两**点零五分 | 走 `countWithUnit`，不是「二点」 |
| 12:00 | 下午十二点 | |
| 00:00 | 上午十二点 | 和英文包的 "twelve AM" 一致 |
| 23:59 | 下午十一点五十九分 | |

另有 `ColloquialTime`（口语时间，「差一刻九点」这种）也加了中文表，`Format()` 按
`soundPackLanguage` 选表。但那条路走**系统 TTS 而不是语音包**，只在用户打开 `colloquial_time`
且 Windows 装了中文 SAPI 语音时才有意义——优先级低于上面这个语序分支。

## 4. 已知取舍

**精度封顶在十分位。** `NumberReader.ConvertTimeToSounds` 里的百分位短形式分支写死了
`getLocale() == "en"`（`NumberReader.cs:109-120`），中文走不到。所以 `1:23.46` 会读成 `1:23.5`。
对模拟赛车播报够用；要提到百分位需要改基类那一行的 locale 判断，并实现
`GetSecondsWithHundredths`，属于后续可选项。

**圈数的量词。** "还剩2圈"中文应读"两圈"，但 `GetIntegerSounds` 拿不到后面跟的是什么量词，只会读"二"。
这条只影响 2 这一个数，且不影响理解。真要修的话得在调用点（`LapCounter` 等事件）传信息进来，成本
远大于收益。

**"一"的变调。** "一"在量词前会变调（一秒 yì miǎo），单字录音是孤立调值 yī。整段录音机制（§5）
覆盖了最高频的几个组合，其余场合保留孤立调值 —— 母语者完全听得懂，只是略生硬。

## 5. 整段录音机制（可选优化）

`countWithUnit` 在拼接前先查 `SoundCache.availableSounds` 里有没有整段录音：

```
countWithUnit(2, "numbers/seconds")
  → 有 numbers/2_seconds  →  ["numbers/2_seconds"]        整段"两秒"
  → 没有                  →  ["numbers/liang", "numbers/seconds"]   拼接
```

这是 `NumberReaderPtBr.resolveNumberSounds` 的同款做法。**文件夹缺失时自动退回拼接**，所以这些整段录音
纯属加分项，可以随时增删而不改代码。当前语料里包含 12 个：

```
1_hours 一小时    2_hours 两小时
1_minute 一分     2_minute 两分
1_minutes 一分钟  2_minutes 两分钟
1_seconds 一秒    2_seconds 两秒
1_thousand 一千   2_thousand 两千
1_ten_thousand 一万  2_ten_thousand 两万
```

如果试听后觉得别的组合也生硬（比如"三秒""五分钟"），照这个命名加进 `numbers_zh.csv` 重新生成即可。

## 6. 文件夹清单（138 个）

| 组 | 数量 | 内容 |
|---|---|---|
| `0`–`99` | 100 | 零、一 … 九十九 |
| `01`–`09` | 9 | 零一 … 零九，用于"一分零三秒" |
| 单位 | 8 | `hour` `hours` 小时 · `minute` 分 · `minutes` 分钟 · `second` `seconds` 秒 · `tenth` `tenths` 秒 |
| 位值与结构 | 9 | `point` 点 · `hundred` 百 · `thousand` 千 · `ten_thousand` 万 · `oh` 零 · `liang` 两 · `minus` 负 · `zerozero` 零零 · `double_oh` 零零零 |
| 整段录音 | 12 | 见 §5 |

`ten_thousand`（万）和 `liang`（两）是中文新增的文件夹，英文包里没有。其余都沿用英文包已有的文件夹名 ——
**文件夹名是播报逻辑里的标识符，不能翻译**，只有音频内容换成中文。

`zerozero` / `double_oh` 只在 `CarNumber` 读车号时用到，而且中文走的是
`NumberReaderFactory.IS_ENGLISH == false` 的分支（`CarNumber.cs:41`）直接整数朗读，用不上这两个。
保留是为了兜底。

`WholeAndFractionalMessage`（`Utilities.cs:458`）会先找 `numbers/3point5` 这类合成音，找不到就退回
`[3, point, 5]`。中文不录这些合成音，走退回路径，读出来是"三点五"，正确。

**54 个用例**覆盖上面两张表——整数 30 条、时长 14 条，外加钟点 10 条

## 8. 接入 CrewChief

```bash
cp src/NumberReaderZh.cs ~/Projects/CrewChiefV4-main/CrewChiefV4/NumberReaderZh.cs
cd ~/Projects/CrewChiefV4-main && git apply ~/Projects/CrewChief_CN_VoicePack/patches/crewchief-zh-numberreader.diff
```

补丁做三件事：`NumberReaderFactory` 增加 `zh` / `zh-cn` 分支、`CrewChiefV4.csproj` 编译新文件、
`UnitTest/Misc/TestNumbersInMessages.cs` 增加中文用例。

运行时靠语音包里的 `sound_pack_language.txt` 选中，内容写 `zh` 或 `zh-cn`。这个文件的第一行会被
`AudioPlayer.getSoundPackLanguage`（`AudioPlayer.cs:1122`）读进 `soundPackLanguage`，而它读的是
`soundFilesPath` —— 也就是 `override_default_sound_pack_location` 指向的那个目录，所以替换基础包的装法
天然生效。

改成中文之前，语音包里必须已经有 `numbers/` 的中文音频，否则 `QueuedMessage` 会因为找不到文件夹把消息
标成 `canBePlayed = false`，表现为静音。

### ⚠️ 数字音频和补丁必须一起上

`numbers/` 的中文音频**不能**在打上补丁之前先铺进语音包。因为 `sound_pack_language.txt` 还是 `en` 的时候，
CrewChief 用的是 `NumberReaderEn`，它会去要 `numbers/45` 和 `numbers/1point3` 这类文件夹 —— 前者被我们换成了
"四十五"，后者还是英文原声，结果是中英混读的"四十五 point three seconds"。

所以顺序是：

| 步骤 | `sound_pack_language.txt` | 铺哪些音频 |
|---|---|---|
| 现在（未打补丁） | `en` | 只铺 `spotter/` 和 `radio_check/` |
| 打补丁并在 Windows 上编译后 | `zh` | 加铺 `numbers/`，之后才是工程师播报 |

spotter 和 radio_check 没有这个问题 —— 它们不经过 `NumberReader`，所以现在就能单独装。

### 顺带的一个好处：自动更新会停

`SoundPackVersionsHelper.parseUpdateData`（`SoundPackVersionsHelper.cs:121`）按语言在更新 XML 里找对应的
`<language>` 节点。上游没有 `zh` 节点，所以匹配不到；而那段兜底逻辑只在 `soundPackLanguage == null` 时才跑，
此时它是 `"zh"`。结果是**一个更新包都不会注册**，`latestSoundPackVersion` 保持 -1，自动更新器不会用英文包
覆盖掉中文包。

这不是刻意设计的，是语言标签的副作用，但对我们正好 —— 不需要额外去关更新开关。反过来说，中文包以后要做
自动更新，得自己搭一份更新 XML。
