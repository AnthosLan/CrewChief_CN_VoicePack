# 踩坑与经验总结

> 本文收录实测结论、失败教训、注意事项与风险登记——**「为什么这么做」和「哪里会翻车」**。
> 流程、参数与命令见[制作方案](中文语音包制作方案.md)；许可见[许可与分发](许可与分发.md)。

大部分条目的代价是真实的机器时间或返工，写下来是为了不再付第二次。

---

## 一、被否决的方案

| 方案 | 结果 | 原因 |
|---|---|---|
| macOS 原生中文 TTS 做 baseline | ❌ 更差 | 共振峰合成的机械感被一起克隆进去；`收到` 出现 576ms/音节 的拖音异常 |
| CrewChief 自带真人语音做 baseline | ❌ 放弃 | 效果不佳，且涉及署名个人（Geoffrey Lessel、Matt Orr 等）的声纹 |
| warm / full / broadcast EQ | ❌ 未采用 | 试听后选定 radio |
| baseline 从 14 秒扩到 39 秒 | ⚠️ 收益有限 | 音高标准差仅从 37.0Hz 降到 32.7Hz（−12%），XTTS conditioning 在 15 秒左右接近饱和。但成本已付，保留 |

## 二、XTTS 中文的固有脾气

### 2.1 中文 TTS 念拉丁字母不可靠

同一个根因在五个地方连续撞到，**是稳定行为不是随机抖动**，`--attempts 8` 重跑无效：

| 现象 | 实测 |
|---|---|
| `bar` / `PSI` 被 QA 判异常 | 单音节拉丁词时长落在中文阈值外 |
| `GTC` 三个字母 | **1.73 秒**，重跑无效，稳定复现 |
| `DTM赛车` | 截断到 **0.21 秒**（光两个汉字也要 0.34 秒） |
| `DRS 不再可用` | **0.49 秒**，比四个汉字单独念还短 |
| `DRS` 在句中 | 只占 **0.25 秒**，三个字母名至少要 0.5 秒 |

由此定下判断标准：**主体是英文缩写或专有编号的播报，整个文件夹不做，回落英文原音。**

语音包覆盖在英文包副本上，**不发的文件夹自动播原来的英文**，所以「不做」是可用选项而不是缺失。
据此排除 **60 个文件夹 / 202 条音频**：车辆组别号（GT3/GT300/LMP2/DTM/Carrera Cup）、组别编号
（Group A/C/5）、`overtaking_aids` 整个分类（DRS/KERS/push-to-pass）。加上原有的车手名和弯角名，
完整清单见[制作方案 §3.2](中文语音包制作方案.md)。

排除规则在 `make_chief_inventory.py` 的 `SKIP_EXACT` 与 `DROP_CLASS_PATTERN`，重新切语料自动生效。

### 2.2 拉丁字母与汉字之间不能留空格

XTTS 会在空格处断句并吞掉后半段：`DRS 不再可用` 只有 0.49 秒，`GT4 车` 截断到 0.22 秒。
`fix_translation.py` 的 `TERM_FIXES` 里有一条全局去空格规则兜底。

### 2.3 短句必须开多候选

一两个汉字是 XTTS 最不稳的地方——会在音节前后补一段幻觉音，或者干脆把音节念两遍。

波次 1 的 1921 条用默认 `--attempts 1` 生成，`qa_pack.py` 报出 **9 条异常**，全是 2–5 音节的短句：
6 条过短（最极端的 `你进来了` 只有 0.13 秒 / 4 音节 = 33 ms）、3 条过长。

根因是 `pick_best_candidate` 有 `--min_ms_per_syllable`（默认 90）这道闸，但**只有一个候选时它没得选**，
只能把不合格的返回。对这 9 条按下面的参数重跑后异常清零，语速范围从 33–548 ms/音节收敛到 93–419，
整批只花 66 秒：

```bash
--attempts 5 --attempts_max_syllables 0
```

**更省事的做法是一开始就对短句开多候选，而不是事后补。**

⚠️ **重跑之后必须重建 `subtitles.csv`**——`pilot_mac.py` 在收尾时按**本次跑过的行**重写字幕文件，
所以只重跑 `flags/yellow_flag/6.wav` 会让那个文件夹 9 条音频的字幕只剩 1 行，其余 8 条在覆盖层上
什么都不显示。而音频本身是好的，听不出问题，只有对着 CSV 逐条比对才会发现。

补救办法是重跑后**从最终 CSV 重建全部 `subtitles.csv`**，并校验「每个 wav 都有字幕且文本一致」。

## 三、机器翻译错在哪

**机翻结果不能直接进 TTS。** 通读和脚本扫描各能发现一半，两种都要做。

### 3.1 波次 1：1452 条改了 404 条

错误不是随机分布的，按危险程度排：

| 类型 | 例 | 后果 |
|---|---|---|
| **反义** | `safety car in`（进站）→「出现」；`gone off`（冲出赛道）→「脱困」；`reeling you in`（追近）→「套你圈」 | 车手照做就是反向操作 |
| **同一术语多种译法** | `spotter` 在 acknowledge 一个分类里出现 8 种译法，含「报站」（公交车报站名）、「领航员」（那是拉力 codriver） | 听起来像换了个人在说话 |
| **量纲错** | `2 tenths`（零点二秒）→「百分之二十」 | 数值完全错 |
| **片段直译** | `laps ahead` →「圈数领先」，中文量词必须跟在数字后面才拼得出「你三圈领先」 | 拼出来不成句 |
| **书面语** | `go, go, go` →「去，去，去」 | 喊不出口 |

前三类靠通读发现，后两类靠脚本扫描（残留数字、省略号、悬空逗号、繁体字、中文夹空格）。
**两种都要做，各自会漏掉对方那一半。**

### 3.2 波次 2：新增三类（1173 条改了 212 条）

前一波已知的错照旧，另外新增：

| 类型 | 例 | 为什么难发现 |
|---|---|---|
| **单位当成别的东西** | `bar`（压力单位巴）→「轮胎监测」；`psi` →「胎压」 | 译文本身像个正经术语 |
| **原文 typo 被顺着译** | `get some head into these brakes`（head 是 heat 笔误）→「给刹车**降温**」 | 意思正好反了 |
| **同义词全译成一个词** | hypersoft / ultrasoft / supersoft 三种配方都叫「超软胎」 | 单看每条都对 |

还有一条 `cooking`（过热）被系统性译成「磨损」共 14 条，「你的左前胎在磨损」读起来完全通顺——
**译文越通顺越难发现，只能对着原文逐条读。**

### 3.3 波次 3+4：组别名不能翻译

GT3、GTE、Group C、LMP2、DTM 这些是专有名词，中文车手也说原名。机翻的处理五花八门：
`GTC` 和 `GTE` 都译成「GT」——**尾字母丢失，两个不同组别变成同一个**；`Group 6` 译成「组别」，
数字没了。共 61 条改回原文。

### 3.4 术语表要在开跑前配齐

波次 2 第一次跑到 294 条时发现，它的高频词几乎全不在术语表里——`penalty` 117 处、`track limits` 98 处、
`stop-go` 41 处、`serve` 33 处、`locking` 28 处，加起来 300 多处靠模型自由发挥。**停掉重跑**，术语表从
45 条扩到 82 条。代价 85 分钟机器时间，换来的一致率：

| 术语 | 一致率 |
|---|---|
| `track limits` → 赛道界限 | 65/66 |
| `wear` → 磨损 | 29/29 |
| `pressures` → 胎压 | 20/20 |
| `locking` → 抱死 | 25/28 |

对照波次 1 的 `spotter` 出现 8 种译法，这次没有同类问题。**开跑前先扫一遍语料的高频术语**，
比事后写几百条修正划算得多。

⚠️ **术语表按无线电口语选词，不是按词典。** 一开始写 `aero = 空气动力套件`，结果满屏「一些轻微的
空气动力套件损坏」——工程师不会这么喊。改成「空力」。

### 3.5 修正表要跨波次继承

波次 2 定的「空力」「标准胎」口径到了波次 3 全丢了，`aero` 又变回「空气动力套件」。
`fix_translation.py` 的 `--corrections` 接受多个文件，后面的覆盖前面的，**把前几波的修正表一起传进去**：

```bash
--corrections chief_wave1_corrections.csv chief_wave2_corrections.csv chief_wave34_corrections.csv
```

只对最后一个（本波）文件报「未命中」——继承来的条目匹配不上是正常的，全报出来会淹没真正要看的。

修正表**按 `original_english` 索引**，所以换 prompt 重新翻译后照样生效。

⚠️ **修正表里含逗号的英文必须加引号。** 不加的话 CSV 会把它拆成三个字段，第二个字段（英文的后半截）
被当成中文译文写进语音包。`fix_translation.py` 有字段数校验会直接报错退出，别绕过它。

### 3.6 UI 文案的错法和电台播报不一样

同一个 qwen2.5:14b，换成翻软件界面，错误类型基本换了一套。前两波（U1 120 条、U2 490 条）实测：

**共同点是「译文碰撞」——不同的设置项译成同一句话。** 属性列表里这些行是挨着的，
碰撞意味着用户看到两个一模一样的设置项，没法知道哪个是哪个。肉眼查不全，
`qa_uitext.py` 加了重复检测，U2 一跑就抓出四组 11 行，其中三行一组的
（`Launch pCARS` / `pCARS 2` / `pCARS 3`）是通读时完全没注意到的。

**① 缩写被展开成全称。** 这是 UI 独有的，也是最贵的一个：

| 英文 | 机翻 | 问题 |
|---|---|---|
| `rF1 install path` | rFactor 安装路径 | 和下面一条**变成同一句** |
| `rF2 install path` | rFactor 安装路径 | ↑ |
| `ACS install path` | Assetto Corsa 安装路径 | 属性列表里认不出是哪个游戏 |
| `RBR install path` | Richard Burns Rally 安装路径 | 同上 |

属性列表里这几行是相邻的，用户就是靠缩写认自己那个游戏。**展开等于把两个设置项合并成一个。**

⚠️ 讽刺的是这是术语表招来的：表里写了 `rFactor = rFactor`、`Richard Burns Rally = ...`，
模型就顺手把缩写"补全"到术语表里的形式。**术语表收产品全称时，必须同时把缩写钉死成它自己。**
另外在 prompt 里加一条硬规则（`NEVER expand an abbreviation`），两道都要。

**② 产品名和角色名撞车。** 术语表同时收了 `Crew Chief = Crew Chief（产品名）` 和
`crew chief = 车队工程师（角色）`，模型选了后者，窗口标题成了「车队工程师 - 当前配置方案」。
界面里 119 次 `Crew Chief` 全是程序名，**角色义直接删掉**。

**③ 数量词丢在译文里没有落点。** `updates to apply` 是个计数后缀（界面显示成 `3 updates to apply`），
机翻成「可用更新」，拼出来是「3 可用更新」。要译成「个更新待应用」。

**④ 前缀被整个吃掉。** 和①相反的方向，但后果一样：

| 英文 | 机翻 |
|---|---|
| `R3E launch exe` | 启动程序 |
| `GTR 2 launch exe` | 启动程序 |
| `LMU launch exe` | 启动程序 |
| `AMS launch exe` | 启动程序 |

四条压成一条。这次也是术语表招来的——写了 `launch exe = 启动程序`，模型就把**整个短语连同
前面的游戏名一起替换**。术语表里凡是「前面通常还有个专名」的短语，都要在译法里写明保留前缀。
prompt 里另加一条 `Do not DROP words either`。

**⑤ C# 类型名被翻译。** 见 §6.4，`Type.GetType(name, throwOnError: true)` 会直接抛异常。

**⑥ 一词多译，比电台那批更密。** `messages` 在相邻两行出现「播报」和「消息」、`devs` 出现
「开发者」和「开发人员」、FCY 在四行相邻设置里出现「赛事控制员/赛事控制/赛事黄旗」三种、
`Crew Chief` 一半带空格一半不带。UI 是一屏能同时看到十几条的地方，不一致比电台里更刺眼——
这类全部收进 `fix_uitext.py` 的 `TERM_FIXES`，不写进修正表。

**结论和第二阶段一样：开跑前先扫本波高频词补术语表。** U2 跑到 49/490 时抽查发现①，
停下来改术语表重跑，比跑完 490 条再写 30 条修正划算得多。④⑤ 是跑完才发现的，
用修正表补了 44 条——**代价比①大约三倍**。

**⑦ 角色译错。** `Chief`（车队工程师）在 U3 里出现两种错译：4 条译成「首席」（职位词残片，
不是人），4 条译成「领航员」——那是拉力赛的 co-driver，CrewChief 里是另一个角色，
而且**语音包里真有领航员**，所以这个错不是无害的。同一批里 `Spotter` 也被译成过领航员。
「首席」可以全局替换（它没有正确用法），「领航员」不行，得逐条改。

**⑧ 术语表用力过猛会砸到别的词。** 为了统一「应用程序 / 应用」，加了一条 `应用 → 程序`，
结果把 `Steam 应用 ID` 也改成了 `Steam 程序 ID`，24 行里出现三种写法，其中一行还被自动断行
切成 `Steam 程\序 ID`。改成只替换 `应用程序`，另加一条把三种写法都归到 `Steam app ID`。
**归一化规则要写得比想象中更窄。**

四波实测：

| 波 | 条数 | 人工修正 | 比例 |
|---|---:|---:|---:|
| U1 主界面 | 120 | 19 | 16% |
| U2 属性名 | 490 | 44 | 9% |
| U3 帮助文本 | 469 | 10 | 2% |
| U4 次要对话框 | 226 | 10 | 4% |
| **合计** | **1305** | **83** | **6%** |

比音频那四波（23%）低得多，因为界面文案句式规整、上下文明确。**但错法更隐蔽**——
音频错了听得出来，界面碰撞、标识符被译、折行吞字，都只有脚本查得出来。
U3 修正率最低（2%）不代表质量最好，而是长文本里大部分问题是用词不一致，
被 `TERM_FIXES` 收掉了 161 行。

## 四、脚本自身踩过的坑

### 4.1 数字归一化正则把 `GT300` 变成「GT3零」

**不是模型错译，是 `normalise_numerals` 的正则**：`(?<![A-Za-z])(\d{1,2})` 在 `GT300` 里匹配到末尾的
`00` 并转成「零」。在修正表里写 `GT300,GT300` 也没用——**归一化跑在人工修正之后**，三层顺序不能换。

正则已改成 `(?<![A-Za-z\d])`，同时排除字母和数字前缀。这类 bug 只在「字母+3 位数字」上触发，
前两波的语料里恰好没有这种模式，**换一批语料才暴露**。

### 4.2 `qa_pack.py` 的音节计数改了三版

原来只数汉字，把拉丁字母当 0 音节，含 DRS/KERS 的条目全部虚报「过长」。改成逐字母计数后又矫枉过正，
把 `别忘了用KERS` 报成「过短」。靠对照实验定的案：

| 文本 | 时长 |
|---|---:|
| `别忘了用` | 0.55s |
| `别忘了用KERS` | 0.85s |
| `别忘了用凯尔斯` | 1.03s |

KERS 确实发音了（多 0.30 秒），但 XTTS 把它当**一个词**而不是逐字母拼读。最终规则：单个字母算
1 音节，缩略词整体算 2 音节。

### 4.3 音频链里重采样必须在归一化之前

带限插值会在瞬态上过冲，反过来会让 16-bit 写入削波。这是修过的 bug（`pilot_mac.py:302`），
`qa_pack.py` 的削波检查就是它的回归防线。

### 4.4 `fix_translation.py` 不带 `--corrections` 一直是崩的

`load_corrections()` 在路径为空时 `return {}`，调用方却是 `corrections, own_keys = ...`，
于是 `ValueError: not enough values to unpack`。

四波语料每次都带着 `--corrections` 跑，所以没人撞到——但模块文档里写着的
`--report_numerals`（只看不写）恰恰是不需要修正表的用法，那条路从写出来就没通过。
改成 `return {}, set()`。

教训：**文档里写了的用法，至少手跑一次**。

### 4.5 自动断行把拉丁词切成了两半

`fix_uitext.py` 的 `insert_breaks` 是为了绕开 §6.1 那个「CrewChief 折行吞字」的坑写的：
在 ≤44 字处按标点插 `\`。第一版只找标点，找不到就在第 44 字硬切——**结果 14 行被切在
拉丁词中间**：

```
Steam a\pp ID        trackLandmar\ksData.json
211\500              rFactor2SharedMemoryMapPlug\in64.dll
```

中文可以在任意两字之间断行，文件名和英文词不行。修法是硬切点落在
`[A-Za-z0-9._/-]` 连续段内时退到段首。

⚠️ 更值得记的是**验证方法一开始也是错的**：我用
`[A-Za-z0-9._/-]\\[A-Za-z0-9._/-]` 去找「被切开的词」，它把 `Steam app\ID` 也算成错误——
那里原本就是个空格，在空格处换行完全正确。**正确的判据是「除空白外没有字符消失」**：

```python
re.sub(r'[\s\\]', '', wrapped) == re.sub(r'[\s\\]', '', original)
```

这条断言已经写进 `fix_uitext.py`，不通过直接 exit。整个脚本存在的理由就是 CrewChief 折行会
吞字，自己再吞一个字就太讽刺了。468 行逐行验证通过。

### 4.6 zsh 不给未加引号的变量做分词

```bash
C="a.csv b.csv c.csv"
python3 scripts/fix_uitext.py --corrections $C ...   # ← zsh 传的是【一个】参数
```

bash 会把 `$C` 拆成三个参数，**zsh 不会**。脚本里 `os.path.exists()` 对那个拼起来的长路径
返回 false，于是静默跳过——四波全部输出「人工修正 0 条生效」，而文件照样写出来了。

要么显式写全部参数，要么用 `${=C}`。**这类失败不报错，只是结果不对**，和本文其他条目是同一类。

## 五、装包陷阱

### 5.1 ⚠️ 不要装到 `alt/` 目录

CrewChief 在使用非默认工程师语音包时，会**强制**从基础包读取 `spotter*` 和 `radio_check*`
（[Sounds.cs:1147-1162](CrewChiefV4/Audio/Sounds.cs:1147)）：

```
选了 alt 语音包 + 公路赛：
  spotter* / radio_check*  →  强制从【基础包】读（英文）
  其余所有 voice 文件夹     →  从 alt 包读
```

按 autovoicepack README 的装法（拷到 `Sounds\alt\`），结果是**工程师说中文、spotter 永远说英文**——
而 spotter 恰恰是比赛中出现频率最高的播报。正确装法见[制作方案 §7](中文语音包制作方案.md)。

### 5.2 防覆盖的实际机制

CrewChief 不会静默覆盖，它只把语音包下载按钮点亮，用户点了才下载。按钮亮不亮看
`latest > current`（[SoundPacks.cs:117](CrewChiefV4/UserInterface/SoundPacks.cs:117)），`current` 取自语音包根目录的
`sound_pack_version_info.txt`，`latest` 按**语言**从上游 XML 取：

| 语言标记 | 取到什么 | 结果 |
|---|---|---|
| `zh`（打了补丁的构建） | 上游 XML 没有 zh 段，`voiceMessageUpdatePacks` 为空 | 按钮永远灰，天然免疫 |
| 空（原版程序） | [MainWindow.cs:607](CrewChiefV4/UserInterface/MainWindow.cs:607) 的 `soundPackLanguage == null ? "en"` 回落到 en，拿到真实英文版本号 | 上游一发新版按钮就绿，需要把 `current` 撑大 |

⚠️ `-skip_updates` **不能**当防线。它只跳过 `AutoUpdater.Start()`（程序本体更新），语音包的
XML 照样下载解析（[MainWindow.cs:598-608](CrewChiefV4/UserInterface/MainWindow.cs:598)）。

### 5.3 ⚠️⚠️ nAudio 的设备选择能让整个语音包看起来完全坏掉

**Windows 验收里最耗时间的一个问题，花了五轮往返才定位。而且它跟语音包毫无关系。**

症状具备欺骗性：一点声音都没有（连启动的无线电测试都没有），但日志里满是
`Sound: spotter/car_left=(spotter/car_left)` 这类行，**一行报错都没有**。看起来像是语音包坏了。

根因是 **CrewChief 不用 Windows 默认输出设备**，它自己存了一个设备 GUID
（`NAUDIO_DEVICE_GUID_MESSAGES`），日志里这一行就是它当前用的：

```
Sound: Detected saved message audio output device: 扬声器 (Realtek(R) Audio)
```

所以「别的程序都有声音」**完全不能**排除音频问题——那些程序走的是默认设备，CrewChief 不是。
用户实测时正是被这一点误导：视频播放正常，于是判断问题在语音包。

三条排查路径，按性价比排：

| 手段 | 作用 | 代价 |
|---|---|---|
| 关掉 `use_naudio` | 改用 `System.Media.SoundPlayer`（[Sounds.cs:2070](CrewChiefV4/Audio/Sounds.cs:2070)），**直接播到 Windows 默认设备**，绕开设备选择 | spotter 失去打断能力，见下 |
| 主界面换 `Messages playback device` | 正解 | 无 |
| 删 `%LOCALAPPDATA%\Britton_IT_Ltd` | 全部设置回默认 | 连 Override 路径一起清掉 |

**第一条是最好的诊断手段**（一分钟、能直接定性），但**不能当长期方案**：
`SoundCache.InterruptCurrentlyPlayingSound` 只在 `playWithNAudio` 为真时才工作
（[Sounds.cs:2305](CrewChiefV4/Audio/Sounds.cs:2305)），关掉 nAudio 之后 spotter 再也不能打断工程师
（[AudioPlayer.cs:2161](CrewChiefV4/Audio/AudioPlayer.cs:2161)）。实测对比：

| 配置 | 截断率 | 副作用 |
|---|---|---|
| nAudio 开 | 15 条里 4 条被切（27%），最狠的只播了 0.20s / 全长 0.80s | 「左边有车」只听到「左」 |
| nAudio 关 | 0 | spotter 排在工程师长句后面，贴身缠斗时晚两秒到 |

两害相权仍应保留 nAudio——晚到的盲区提醒等于没有，而被截断的至少传达了方向。

**教训：以后遇到「装完没声音」，第一件事是让用户报 `Detected saved message audio output device`
那一行，而不是去查语音包。** 语音包是否装对有独立判据（见 5.6）。

### 5.4 ⚠️ 卸载重装 CrewChief 不重置任何配置

用户在排查 5.3 时卸载重装了一次，**毫无变化**——这本身就是个有诊断价值的现象。

配置不在程序目录里，在 `%LOCALAPPDATA%\Britton_IT_Ltd`（日志开头的 `UserConfigFolder:` 那一行），
卸载程序不碰它。设备选择、音量、全部属性都原样躺在里面，重装后一字不差读回来。

上游源码对这个文件夹的注释就一句（[DataFiles.cs:50](CrewChiefV4/DataFiles.cs:50)）：
*"The only thing you'd want to do with this is zap the folder out of desperation"*。

所以排查配置类问题时，「重装试试」是**无效动作**，别浪费用户时间。

### 5.5 ⚠️ 界面文案的用户覆盖层是二选一，不是合并

[Configuration.cs:212](CrewChiefV4/Configuration.cs:212)：

```csharp
var overrideFileName       = getUserOverridesFileLocation("ui_text\\en.txt");
var legacyOverrideFileName = getUserOverridesFileLocation("ui_text.txt");
if (File.Exists(overrideFileName))            LoadAndMerge(dict, overrideFileName);
else if (File.Exists(legacyOverrideFileName)) LoadAndMerge(dict, legacyOverrideFileName);
```

只要 `%LOCALAPPDATA%\CrewChiefV4\ui_text\en.txt` 存在，我们装的 `ui_text.txt` 就被**完全忽略**。
而且 `LoadAndMerge` 内层是 `catch (Exception) { }`，**失败完全静默**，界面就是保持英文，没有任何提示。

容易混淆的是：**安装目录**下的 `ui_text\en.txt` 是上游自带的英文底本，本来就该在那儿，不挡路。
挡路的只有**用户目录**下的那个。INSTALL 里必须把这两个路径并排列出来，否则用户会误删底本。

编码方面没有坑：`new StreamReader(path)` 默认 UTF-8 且探测 BOM，带不带 BOM 都能读。

### 5.6 判断语音包是否装对：只看一个数

`Finished preparing sounds cache, found N driver names and **M sound sets**`
（[Sounds.cs:440](CrewChiefV4/Audio/Sounds.cs:440)）。`M` 是有音频的 `<分类>/<文件夹>` 对数。

**本包的 1264 个文件夹名全部来自英文包，一个新的都不加**，所以正确合并后 `M` 应当与装包前完全一致。
实测三组数据：

| 状态 | sound sets | 说明 |
|---|---|---|
| 英文包基线 | 3247 | |
| 装了中文包（含 `numbers/`） | 3261 | **+14 = 中文特有的数字文件夹**（`liang`、`ten_thousand`、`1_minute` 等），证明 `numbers/` 被装上了 |
| 恢复英文 `numbers/` 后 | 3247 + personalisation | 我们的包贡献 **0**，用法 A 的正确状态 |

这个不变量非常好用：**+14 就是「装了不该装的 numbers」的硬证据**，比让用户去翻文件夹可靠得多。
数字变少则说明原目录被整体替换而不是合并。

## 六、CrewChief 代码里对中文不友好的地方

第三阶段（UI、时间播报、语音指令）开工前通读源码找出来的，都是「英文能跑、中文会出错」的地方。
6.1 / 6.2 / 6.4 必须先处理再动手翻译，否则译完了才发现结构不对。

### 6.1 ⚠️ 帮助文本折行会吞掉汉字

[Utilities.cs:672](CrewChiefV4/Utilities.cs:672) 的 `NewlinesInLongString` 给 `_help` / `_tooltip`
做自动折行（默认 44 字符）：

```csharp
int splitIndex = _line.Substring(0, maxLength).LastIndexOf(" ");
if (splitIndex == -1) splitIndex = maxLength;   // 找不到空格，硬切
result += _line.Substring(0, splitIndex) + NewLine;
_line = _line.Substring(splitIndex + 1);        // ← 跳过 splitIndex 位置的字符
```

英文按空格断行，`splitIndex + 1` 跳过的正是那个空格，没有损失。**中文没有空格**，
`LastIndexOf(" ")` 返回 −1，于是在第 44 个字符处硬切，`+1` 跳过的就是一个**汉字**。

实测（Python 复刻同一段逻辑）：100 个汉字折行后剩 98 个，**每 44 字丢 1 个**。

en.txt 的 469 条 `_help` / `_tooltip` 里，**423 条的最长段超过 44 字符**（平均 98、最长 602），
全都会中招。丢字在界面上看不出来，只会觉得句子读着别扭——和「单条重跑毁字幕」是同一类
静默故障。

**解法（不用编译）**：翻译时插显式换行符 `\`，保证每段 ≤44 字。这个标记 en.txt 文件头本来就
说明了（"A few _help or _tooltip strings include a \ which inserts a newline"），是上游支持的用法。
必须写成脚本校验，人工看不出来。

> 这也是上游的潜在缺陷——英文里遇到 44 字符内无空格的长 URL 同样会丢字符，只是罕见。
> 修 `Utilities.cs` 要编译，而 UI 中文化的卖点正是「原版程序可用」，所以选了插 `\` 这条路。

### 6.2 时间播报按英文语序拼片段

[CommonActions.cs:814](CrewChiefV4/Events/CommonActions.cs:814) 的 `reportCurrentTime()` 分两条路：

| 条件 | 走法 | 与语音包的关系 |
|---|---|---|
| `colloquial_time` 开 **且** `SoundCache.SetUpTTS()` 成功 | `ColloquialTime.Format()` 的文本喂**系统 TTS**（`fragment.allowTTS = true`） | 无关，要用户装了中文 SAPI 语音 |
| 否则 | 语音包文件拼 `hour` + `folderOh` + `minute` + `am/pm` | 用我们的音频 |

第二条是多数人听到的，而它**按英文语序拼**。我们已经发了 `alarm_clock/am`=上午、`pm`=下午，
所以现在装中文包会念成「八 零 五 上午」。

同一个方法里已经有 `if ("it".Equals(AudioPlayer.soundPackLanguage))` 的意大利语分支，
加 `zh` 分支是照抄现成模式的几行代码。

⚠️ **所以「`ColloquialTime` 中文化 60 个映射」这个说法是误导的**——那 60 个映射只影响第一条路
（系统 TTS），价值远低于第二条路的语序分支。工作分解表已按这个结论拆成两项。

### 6.3 语音指令没有 `{locale}` 机制，但有整份替换机制

[Configuration.cs:277](CrewChiefV4/Configuration.cs:277) 的 `LoadSpeechRecognitionConfig()` 给
`LoadConfigHelper` 传的第二个参数是 **null**，所以 `speech_recognition_config/zh.txt` 这种
按语言合并的路子**不存在**（UI 的 `ui_text/{locale}.txt` 有，这个没有）。

但有更合适的东西：`Documents\CrewChiefV4\speech_recognition_override.txt` 存在时
**整份替换、不做任何合并**（[Configuration.cs:16](CrewChiefV4/Configuration.cs:16) 的注释写明了
设计意图就是「让用户删掉用不上的指令」）。这正好是「只保留 30–50 条中文指令」要的机制：
原版程序可用、不用编译、程序更新不会覆盖。

⚠️ 用这个文件时**必须显式写 `language` 和 `defaultLocale`**——代码在缺失时会补成 `en` 和空串，
静默回到英文识别。

### 6.4 ⚠️ en.txt 里有 913 条不是显示文本，是标识符

这是 UI 版的「文件夹名不能翻译」，而且占比大得多——**2218 条里有 913 条（41%）** 根本不该译。
按 key 后缀分：

| 后缀 | 条数 | 值的样子 | 译了会怎样 |
|---|---:|---|---|
| `_category` | 457 | `UI_STARTUP_AND_PATHS`、`TIMINGS;VIPS` | `Enum.TryParse` 失败（[PropertyFilter.cs:46](CrewChiefV4/UserInterface/PropertyFilter.cs:46)），该设置项从分组里消失 |
| `_filter` | 230 | `ASSETTO_64BIT;ASSETTO_PRO`、`!RF1` | 解析成 `GameEnum` 失败，设置项在所有游戏下都显示或都不显示 |
| `_metadata` | 222 | `RESTART_REQUIRED` | `metadataFlag == "RESTART_REQUIRED"` 精确比较，「需要重启」提示不再出现 |

三种都是**静默失效**：字符串照样加载，只是不再匹配。这三种共 909 条，值都符合
`^!?[A-Z0-9_]+(;[A-Z0-9_]+)*$`，已逐条核对。

它们的显示名是另外的 key（`ui_startup_and_paths_category_label` 这种 `_label`），那些**要译**。

还有第四个后缀，是译到一半才发现的：

| 后缀 | 条数 | 值的样子 | 译了会怎样 |
|---|---:|---|---|
| `_listprop_type` | 4 | `CrewChiefV4.Audio.AudioPlayer+TTS_OPTION` | `Type.GetType(name, throwOnError: true)`（[ListPropertyControl.cs:22](CrewChiefV4/UserInterface/ListPropertyControl.cs:22)）——这个**不是静默失效，是直接抛异常** |

四条全被机翻处理了，`CrewChiefV4.Audio.MinPriorityForInterrupt` 变成
`CrewChiefV4.音频.最低优先级中断`。它们的选项标签是另外的 `*_listprop_value_N` key，那些要译。

⚠️ 反过来也有陷阱：`_exe` / `_params` / `_port` / `_path` 这几个后缀看着像机器值，其实是标签
（`ACS install path`、`ACC UDP port`），**要译**。别按「名字像不像标识符」判断，要看代码怎么消费。

排除规则写在 `make_uitext_inventory.py` 的 `INVARIANT_SUFFIXES`，`qa_uitext.py` 会拦截给这些
key 写译文的行为。四个后缀共 **913 条**，剔掉之后 UI 真实工作量从 2222 降到 **1305 条**。

### 6.5 字幕覆盖层的控件文案硬编码，中文化覆盖不到

`ui_text.txt` 能覆盖主窗口和属性页，但**覆盖不到字幕覆盖层的设置面板**。那些字符串是硬编码在
[SubtitleOverlay.cs](CrewChiefV4/Overlay/SubtitleOverlay.cs) 的构造调用里：

```csharp
new ElementCheckBox(gfx, "Bold font", fontControls, ...)
new ElementCheckBox(gfx, "Hide controls on startup", fontControls, ...)
new ElementButton(gfx, "Save settings", fontControls, ...)
```

不走 `Configuration.getUIString`，所以只能改代码。**字幕正文不受影响**，正文来自
`subtitles.csv`，是中文的。

这一项**不打算做**：覆盖层设置是一次性调完就收起来的东西（见下面的 Ctrl+Shift），
为它改代码不划算，而且会让「原版程序可用」这条前提失效。

顺带记两条覆盖层的实测结论，都是 UI 上没写的：

- **默认关闭。** `enable_subtitle_overlay` 默认 `False`，标了 `RESTART_REQUIRED`。
  「装了包没看到字幕」是正常的，不是缺陷——INSTALL 里必须写这一步。
- **`Ctrl + Shift` 收起／展开控件面板**（[SubtitleOverlay.cs:473](CrewChiefV4/Overlay/SubtitleOverlay.cs:473)），
  界面上完全没提示。而勾选框「Hide controls on startup」只在**启动时**读一次，勾了不会立刻生效。
- 字体不用改。实测中文 Windows 默认字体就能正常渲染汉字，README 里那条「显示成方块改 fontName」
  是防御性说明，不是必做步骤。

### 6.6 上游 bug：`SPOT` / `DONT_SPOT` 会报假错

不是中文专有问题，但会让中文用户误判，所以记在这里。说「开启观察员」之后日志里出现：

```
[Subtitle] You: 开启观察员
ERROR: Speech command 开启观察员 not handled
Sound: acknowledge/spotterEnabled=(acknowledge/spotterEnabled)
```

**指令是生效的**（spotter 开了、应答音播了），但仍记一条 ERROR。原因在
[SpeechRecogniser.cs:3410](CrewChiefV4/SpeechRecogniser.cs:3410)：

```csharp
List<EventResult> results = null;                       // 初始化成 null
if (ResultContains(recognisedSpeech, DONT_SPOT, false))
{ crewChief.disableSpotter(); return results; }          // 干完活返回 null
else if (ResultContains(recognisedSpeech, SPOT, false))
{ crewChief.enableSpotter();  return results; }          // 同上
```

调用方把 `null` 当成「没处理」并报错。英文说 `spotter on` 会报一模一样的错。
**不修**——这是上游的事，我们只在 INSTALL 里说明可以忽略。

## 七、环境依赖的四个坑

按踩到的顺序，四个版本约束都是钉死的，别放宽：

| 现象 | 原因 | 解法 |
|---|---|---|
| `No module named 'torch'` | coqui-tts 0.27 不再声明 torch 依赖（让用户自选 CUDA/CPU 版本） | 单独装 |
| `cannot import name 'isin_mps_friendly'` | transformers 5.x 移除了该函数 | 降到 4.57.x |
| `torchcodec library is required` | torch 2.9+ 强制要 torchcodec，而它又要系统装 ffmpeg | 降到 torch 2.8 规避 |
| XTTS 中文分支报错 | 缺中文 g2p 依赖 | 装 `jieba` `pypinyin` |

另外两条：

- ⚠️ **不要用 `qwen2.5:32b`**：19GB 模型在 16GB 内存的 M1 上会疯狂 swap。用 `qwen2.5:14b`（约 9GB）或云端 API。
- `translate_phrases.py` 的 `--ollama_host` 默认是 `host.docker.internal:11434`（给 Docker 用的），
  本机直接跑必须显式传 `localhost:11434`，否则连不上。
- ⚠️ 翻译输出 CSV 若已存在会被当成断点续跑、用它预热缓存，**改了 prompt 或术语表后必须先删掉**。

**语音指令的实测结论比预期好。** 原本担心中文同音字会让识别率很低，实际用 Windows
自带引擎（阈值 0.75，比 MSSpeech 的 0.5 严）就有 81% 一次通过，被拒的重念一遍全部通过。
而且 CrewChief 的置信度门槛是**自适应**的——按接受/拒绝比动态调整，还能识别「用户重念了」
并主动降低（`Command appears to have been re-tried, lowering threshold`），实测一场里
从 0.75 走到 0.571。所以**不必推荐用户特意去装 MSSpeech**。

唯一表现不稳的是「全部报一遍」（唯一只试一次就被拒的，0.401）。样本太小还不能定论，
需要复测；如果稳定偏低就换个说法。

### 8.2 三个「不是故障」的现象，都被误判过

验收过程中有三件事看起来像 bug，实际都不是。**这三条比真 bug 更值得记**——它们会持续消耗
排查时间：

| 现象 | 真相 |
|---|---|
| 装完一点声音都没有 | nAudio 设备选错，见 §5.3。**五轮往返才定位**，而且和语音包无关 |
| 联机模式几乎不播报 | 那场是**练习赛 + 场上只有 1 台对手车**，CrewChief 本来就没什么可说的。单机那场是正赛 + 10 台车，两者不可比 |
| 说「开启观察员」报 ERROR | 上游 bug，指令其实生效了，见 §6.6 |

第二条特别值得注意：用户拿「联机练习赛」和「单机正赛」对比，得出「联机模式坏了」的结论。
`NumCarsAtStartOfSession 24` 是**服务器车位数**，不是在线车数——`isConnected == 1` 的只有 1 台，
这是正确的。判断语音包是否正常必须用**正赛 + 多台车**。

### 8.3 仍未决的

| 风险 | 状态 |
|---|---|
| **单变体机械感** | 同一句反复听会腻。原包每文件夹 2–7 个变体轮换，中文包目前单变体 |
| **spotter 被打断截断** | 见 §5.3。实测 27%，nAudio 是必要的所以只能接受。若要改善得重做 spotter 那 124 条、压得更短 |
| **9 条帮助文本在拉丁词处断行** | 8 条断在空格处（正常折行），1 条（`console_flush_help`）已修 |
| **数字语音指令被禁** | 整份替换导致上游 1099 条数字读法丢失。本包 45 条没用到数字，零影响；但带数字的宏和「P5 是谁」不可用。补要加约 200 行，会拉低识别率，**暂不补** |
| 第 4、5 项验收 | 用法 B 的前置条件，见 8.1 |

> **脚本能证明「格式对」，证明不了「说得通」。**

这句话在验收后仍然成立，但适用范围小了很多：5308 条里实听了几十条，1305 条里翻了几页。
抽样没发现问题，不等于全量没问题——**译文别扭这类问题只能靠使用者反馈**，这也是标 Beta
而不是正式版的理由。
